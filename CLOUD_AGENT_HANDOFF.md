## Актуализация на 2026-09-01

Этот раздел новее исходной оценки ниже и имеет приоритет при расхождениях.

- `main.rs` читает обязательную `DATABASE_URL`, не выводя её значение.
- `tokio-postgres::Connection` обслуживается в отдельной Tokio-задаче.
- Повторный вызов `fetch_table_meta` устранён; один запрос разбирается одним
  `match`.
- Результат выводится как полная `Vec<TableMeta>` через `Debug`, без частичного
  индексирования `vec[0]`.
- Выполнен успешный живой запуск на `postgres_air`: получены `account`, её
  `reltuples`, `relpages` и базовая статистика `account_id`/`first_name`.
- Для следующего этапа принято решение извлекать полиморфный `most_common_vals`
  как сырой текст PostgreSQL, а `most_common_freqs` — как частоты.
- В `catalog.rs` временно оставлен диагностический `LIMIT 2`.
- `cargo check --workspace` проходит; тестов пока нет; `cargo fmt --all --
  --check` требует только форматирования `catalog.rs`.
- Подробный прогресс записан в GitHub issue №1 и локальном
  `context/issues/0001-data-layer-initialization.md`.

## 1. Замысел проекта

`pg-ray` — исследовательская утилита для анализа скрытого пространства решений
стоимостного планировщика PostgreSQL. Заявлены три направления:

1. поиск точек перелома стоимости между физическими планами;
2. анализ плотности ввода-вывода по кардинальности и затронутым страницам;
3. аудит предикатов, неявных приведений типов и трёхзначной логики `NULL`.

Теоретические ориентиры проекта: конечные модели, сложность алгоритмов, теория
типов, конструктивный подход, MaxEnt и бритва Оккама.

## 2. Фактическое состояние

Проект находится на стадии раннего прототипа первого слоя извлечения данных.

- Язык и сборка: Rust 2024, Cargo workspace.
- Единственный crate: `modules/rust/ray-extractor`.
- Драйвер: асинхронный `tokio-postgres` поверх `tokio`.
- `main.rs` подключается к локальной PostgreSQL, запускает connection future и
  выполняет только `SELECT 1 AS ping`.
- Подготовлены два SQL-запроса:
  - `pg_class.sql` — оценки строк и страниц пользовательских heap-таблиц;
  - `pg_stats.sql` — статистика колонок, включая MCV и histogram bounds.
- Есть ADR 0001 с макрографом исследования PostgreSQL: транспорт, переписывание,
  планировщик, выполнение, чтение, запись, память.
- GitHub issue №1 требует подключение, структуры метаданных, запросы каталогов и
  отображение результатов в Rust. Выполнена только часть подключения и черновики
  запросов.

## 3. Проверенное состояние сборки

Запускалось из корня репозитория 2026-08-24:

```text
cargo fmt --all -- --check  -> FAIL: только форматирование main.rs
cargo check --workspace     -> PASS с предупреждением о resolver
cargo test --workspace      -> PASS, выполнено 0 тестов
```

Cargo предупреждает, что виртуальный workspace использует resolver `1`, хотя
edition 2024 подразумевает resolver `3`. В корневом `Cargo.toml` следует явно
указать `resolver = "3"` после проверки совместимости.

Интеграционный запуск против живой PostgreSQL в рамках этой оценки не выполнялся:
наличие и состояние локальной базы `postgres_air` не предполагаются.

## 4. Решение по модели выполнения

Issue №1 описывает синхронный драйвер `postgres`, зависимости `postgres` и
`serde_json`, а код уже выбрал асинхронные `tokio` и `tokio-postgres`.

Решение Павла от 2026-08-24: **сохранить текущий асинхронный стек**. Проект
рассматривается как потенциально большой, а `tokio-postgres` пока не создаёт
наблюдаемой помехи. Не следует менять драйвер только ради теоретического упрощения.

Практический контракт:

1. продолжать на `tokio` и `tokio-postgres`;
2. обновить формулировку issue №1, чтобы она не требовала синхронный `postgres`;
3. не усложнять архитектуру лишь потому, что runtime это позволяет;
4. вернуться к выбору драйвера только при конкретной измеримой проблеме:
   чрезмерной сложности, неудобстве тестирования, проблемах жизненного цикла или
   отсутствии реальной пользы async-модели.

## 5. Технические долги и риски

### P0 — воспроизводимость репозитория

Почти весь новый каркас сейчас не отслеживается Git:

- корневые `Cargo.toml` и `Cargo.lock`;
- `AGENTS.md`, регламенты и весь `context/`;
- `docs/`, `ocs/`, `pg_class.sql`;
- каталоги `target/` и резервные файлы `*~`.

В репозитории нет `.gitignore`. Новый клон ветки `dev` не получает корневой
workspace и не воспроизводит текущий запуск команд из корня.

### P0 — конфигурация подключения

Строка подключения захардкожена:

```text
host=localhost user=kiryloshakirov dbname=postgres_air
```

Она непереносима и расходится с Definition of Done, где указан `DATABASE_URL`.
Секрет в коде сейчас не виден, но сам паттерн опасен. Нужна конфигурация из
окружения с ясной диагностикой отсутствующего значения.

### P1 — SQL ещё не включён в программу

Файлы запросов существуют отдельно, но `main.rs` их не загружает и не выполняет.
Нет параметров целевой схемы, таблицы и колонки; текущие запросы сканируют всю
пользовательскую статистику.

### P1 — типизация статистики PostgreSQL

`most_common_vals` и `histogram_bounds` в `pg_stats` имеют полиморфное
представление, зависящее от типа колонки. Нельзя заранее считать, что драйвер
сможет безопасно отобразить их в единый Rust-массив. Для первого честного среза
стоит выбрать явное представление (например, текст/JSON на стороне SQL) и
зафиксировать потерю или сохранение типовой информации.

### P1 — модель данных отсутствует

Пока нет структур `Catalog`, `TableStats`, `ColumnStats`, преобразования `Row` в
доменные типы, проверки инвариантов и разделения слоя доступа к данным от CLI.

### P1 — проверки отсутствуют

Нет unit-тестов, интеграционных тестов или зафиксированной матрицы версий
PostgreSQL. Зелёный `cargo test` сейчас означает только успешную компиляцию
тестового бинарника.

### P2 — точность каталожных запросов

- `pg_class.sql` предполагает размер страницы `8192`, хотя PostgreSQL позволяет
  сборки с другим `block_size`; значение лучше получать из сервера.
- Фильтр `relkind = 'r'` исключает partitioned tables и другие отношения. Это
  допустимо только как явно зафиксированная граница MVP.
- `reltuples` — оценка после статистического обслуживания, а не точная
  кардинальность; интерфейс не должен называть её точным числом строк.
- Нужна проверка поведения при устаревшей или отсутствующей статистике.

### P2 — обслуживание connection task

Ошибка фонового connection future только печатается в `stderr`; она не
возвращается вызывающему коду. Для короткого CLI это может скрыть причину
частичного завершения. Следует определить явную политику жизненного цикла задачи.

### P2 — гигиена дерева

Есть три версии ADR (в `docs/adr`, `ocs/adr` и корневой файл с завершающей точкой),
редакторские копии `*~`, два каталога `target/` и два lock-файла. Каноническим
местом ADR согласно `AGENTS.md` является `docs/adr/`; остальные экземпляры нужно
разобрать с Павлом, а не удалять молча.

## 6. Сильные стороны

- Исследовательская цель сформулирована содержательно, а не как набор случайных
  метрик.
- Первый вертикальный срез выбран разумно: сначала наблюдаемые каталожные данные,
  затем модель селективности и стоимость.
- SQL короткий, читаемый и уже извлекает ключевые величины `reltuples`, `relpages`,
  `null_frac`, `n_distinct`, MCV и гистограмму.
- ADR фиксирует широкий предмет исследования и может стать картой последующих
  экспериментов.
- Текущий Rust-код мал и потому ещё легко привести к строгим границам без дорогой
  миграции.

## 7. Рекомендуемый ближайший вертикальный срез

Не начинать пока визуализацию, breakpoints или AST-аудит. Сначала замкнуть issue
№1 минимальным проверяемым контуром:

1. Сохранить выбранный async-стек и синхронизировать с ним контракт issue №1.
2. Добавить `.gitignore`, канонизировать workspace и убрать из будущего коммита
   build/editor artifacts без удаления пользовательских исходников.
3. Читать `DATABASE_URL`; принимать целевые `schema`, `table`, `column` явно.
4. Ввести минимальные доменные структуры таблицы и статистики колонки.
5. Параметризовать SQL и выбрать честное представление полиморфных значений.
6. Выполнить оба запроса и вывести структурированный диагностический результат.
7. Добавить unit-тесты преобразований и один opt-in интеграционный smoke test.
8. Проверить `fmt`, `check`, `test` и живую PostgreSQL, затем обновить issue №1.

Критерий завершения среза: чистый клон репозитория собирается; при заданном
`DATABASE_URL` и цели возвращает типизированные оценки таблицы и статистику одной
колонки; без базы тесты доменной логики остаются воспроизводимыми.

## 8. Что облачному Жене нельзя предполагать

- Не считать незатреканные файлы мусором: это текущая работа Павла.
- Не удалять дубликаты ADR, `*~`, `target/` или lock-файлы без согласования.
- Не считать issue №1 выполненным только из-за успешного ping.
- Не называть `reltuples` точной кардинальностью.
- Не добавлять ORM, конфигурационный framework или сложную архитектуру без
  доказанной необходимости.
- Не возвращать проект к синхронному драйверу без конкретного наблюдаемого
  препятствия и нового решения Павла.
